# Morphinia

Type one word. Get the exact Morphine song and the exact second he says it.

Built as a cassette: the input is the tape window, the left reel searches,
the right reel drops a random word from the catalog so you can discover bars
you didn't know to look for.

Live at **https://oviich.com/lmorphiniya/**.

## Status

Real, running: search, YouTube-timestamp playback, and lines timed by hand
in [tools/timer.html](./tools/timer.html) — see `public/data/songs.json` for
what's live right now (generate it with `npm run build:songs`; it's
gitignored since it's derived data, not source). 258 more songs are already
scraped from Genius and searchable in "not timed yet" mode while they wait
their turn — see [data/README.md](./data/README.md).

## Run it

```bash
npm install
npm run dev
```

Opens at the printed `localhost` URL. `npm run build` produces a static
`dist/` — still no backend for the app itself; it fetches its song data as
plain JSON at runtime (see below) rather than talking to a server.

## How data gets from "timed in the tool" to "live on the site"

This used to be a real gap: the timer tool wrote timestamps to
`data/timing-worksheet.csv`, but the app's song data was baked into the JS
bundle at build time — so a song timed straight in prod just wouldn't show
up until someone noticed, rebuilt, and redeployed. Fixed now:

- `src/lib/loadData.ts` **fetches** `data/songs.json` / `data/allLyrics.json`
  at runtime instead of importing them as bundled modules.
- `scripts/timer-server.js` **regenerates `songs.json` itself, on every
  save** (`SONGS_OUTPUT_PATH` in `.env` — see `scripts/README.md`), using
  the same transform as the CLI script (shared in
  `scripts/lib/build-songs.js`, so the two can't drift apart).

So in prod, the timer tool and the live app are two processes on the same
box, and the timer writes straight into the path the app fetches from — a
save shows up on next page load, no rebuild involved. Locally, the same
`npm run build:songs` output lands in `public/data/`, which Vite serves
as-is (dev) or copies into `dist/` (build) — same fetch path either way,
just regenerated by hand instead of automatically.

## How search works

- `src/lib/search.ts` tokenizes every lyric line into words at startup and
  builds two in-memory indexes: one over precisely **timed** songs, one over
  every **scraped** song regardless of timing status.
- A search tries an exact match in the timed index first (best: jump to the
  exact second), then an exact match in the untimed index ("found it, just
  not timed yet"), then falls back to partial/fuzzy matches in the timed
  index so typos and half-remembered words still surface something.
- Each word's timestamp is estimated from its character position inside its
  line, interpolated between that line's timestamp and the next line's — see
  [data/README.md](./data/README.md) for why that's enough precision without
  hand-timing every word.

## Project layout

```
src/
  components/     Cassette shell, spinning reel buttons, results list,
                   YouTube player (synced, karaoke-style), runaway Genius button
  lib/loadData.ts Runtime fetch of public/data/*.json
  lib/search.ts   Indexing + search + timestamp interpolation
  types.ts        Song / lyric line / search result shapes
public/data/      songs.json + allLyrics.json — gitignored, generated (see above)
data/             Worksheet + template + instructions for the real lyrics catalog
scripts/          Genius API pipeline (songs, lyrics, YouTube links) and the
                   CSV -> app-data build scripts (see scripts/README.md)
postman/          Importable Postman collection for testing the Genius API by hand
tools/            Tap-to-mark timing tool, deployed standalone in prod
                   (see tools/README.md)
```
